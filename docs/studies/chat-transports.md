# GitHub Issues Win; Guests Need Another Lane

The leading candidate is the right foundation. One issue per room in a private, chat-only repo, with comments as messages and a REST poll that sends an ETag, is the only option researched that gives four things at once with zero maintainer infrastructure: authenticated identity, durable history for Macs that sleep, membership, and moderation. It also runs on the `gh` token every colleague already has. Four defaults have to change. A free organization should own the repo, because in a personal repo every collaborator is a writer who can push code and edit or delete anyone's message. One fixed repo-wide URL should be polled with `fetch` and an ETag, not with `gh api` per poll. Each client must set its repo subscription to *ignored*, or every line emails the team. Writes must go out one at a time, paced. What GitHub cannot give is anonymity. It has no anonymous write path, and a relay holding a bot token is exactly the always-on infrastructure the brief rules out. Anonymous users therefore need a second lane where identity is a device keypair and membership is a secret in an invite link. Free Nostr relays can carry that lane with no maintainer infrastructure at all. A Cloudflare Durable Object is the free upgrade (about 120 lines) if guests need durable history and bans enforced by the server. Every peer-to-peer stack fails the sleeping-Mac test unless some peer is always on. Every hosted vendor runs into the fact that a key in a public repo is a public key. Team chat platforms tie the group to a workspace and to per-user tokens. Across all of them the real risk is not the cryptography but the board itself: chat text is hostile input to an app that can type into terminals running Claude Code. It needs a stricter sanitizer and no code path to a drawer.

## The issue room holds up once four defaults change

The candidate is cheaper to run than it looks, because GitHub's REST API makes an idle poll free. `GET /repos/{owner}/{repo}/issues/comments` lists the comments on every issue in a repo, takes a `since` filter and returns a weak ETag ([GitHub REST: issue comments](https://docs.github.com/en/rest/issues/comments)). GitHub states that **"making a conditional request does not count against your primary rate limit if a 304 response is returned"** ([GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). The research confirmed this live: a replayed ETag came back 304 and the rate-limit counter did not move. One fixed URL therefore covers every room in the repo. With 30 colleagues each polling every 3 s, idle traffic costs nothing against the 5,000 requests/hour budget. Each new message costs each reader one counted request, so 300 messages an hour would use about 6% of a reader's quota.

Writes are the tighter bound. GitHub allows **about 80 content-creating requests per minute and 500 per hour**, charges 5 secondary points per POST against a 900-point/minute REST budget ([GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)), and asks clients to send mutations one after another, at least a second apart ([GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). People typing never reach those numbers; a retry loop would.

Latency equals the poll interval, 2–5 s, because GitHub has no production push path to a client behind NAT. `gh webhook forward` is "only designed for use during testing and development" and allows one forwarder per repository ([GitHub: forwarding webhooks with the CLI](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/using-the-github-cli-to-forward-webhooks-for-testing)). The Notifications API asks for 60 s between polls ([GitHub REST: notifications](https://docs.github.com/en/rest/activity/notifications)), and the Events API warns its latency is "anywhere from 30s to 6h" ([GitHub REST: events](https://docs.github.com/en/rest/activity/events)).

**The first default to change is who owns the repo.** "Collaborators can't have read-only access to repositories owned by a personal account" ([GitHub: personal repository permissions](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-personal-account-settings/permission-levels-for-a-personal-account-repository)). In the maintainer's own account, then, every chat member is a writer who can push code and edit, delete or close other people's messages and rooms. A free organization gives finer roles. Every role from Read up can open issues and edit or delete its own comments. Editing, deleting or hiding *anyone's* comments, and locking conversations, are reserved for Write, Maintain and Admin ([GitHub: organization repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)). A dedicated free org that owns a chat-only private repo makes ordinary members Read and moderators Write, and leaves nothing worth pushing.

Membership goes through the collaborators API. The maintainer's board calls `PUT /repos/{o}/{r}/collaborators/{login}` with a `permission` that is "only valid on organization-owned repositories", and is limited to **50 invitations per repository per 24 hours** ([GitHub REST: collaborators](https://docs.github.com/en/rest/collaborators/collaborators)). Invitations **expire after seven days** ([GitHub changelog, 2020](https://github.blog/changelog/2020-02-05-self-expiring-repository-and-organization-invitations/)). The invitee's board finds the invitation and accepts it with `GET` and `PATCH /user/repository_invitations/{id}` ([GitHub REST: invitations](https://docs.github.com/en/rest/collaborators/invitations)). The credential matters: a fine-grained PAT cannot be used "to contribute to repositories where the user is an outside or repository collaborator" ([GitHub: managing personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). `gh`'s OAuth token, issued with the `repo`, `read:org` and `gist` scopes ([gh auth login](https://cli.github.com/manual/gh_auth_login)), can, and it is already on every Mac.

**The second default is notifications.** Every comment POST "triggers notifications" ([GitHub REST: issue comments](https://docs.github.com/en/rest/issues/comments)). Commenting subscribes the author to the thread, and users can choose to watch every repo they can push to ([GitHub: about notifications](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications)). Left alone, a lively room emails colleagues on every line. Each board should set `PUT /repos/{o}/{r}/subscription {ignored: true}` when chat is switched on ([GitHub REST: watching](https://docs.github.com/en/rest/activity/watching)). Ignoring individual threads is not enough, because a thread ignore lapses the moment the user comments again ([GitHub REST: notifications](https://docs.github.com/en/rest/activity/notifications)). The cost is that real @mentions in that repo are silenced too, which is acceptable in a repo that holds nothing but chat.

The remaining limits are soft. Bodies cap at **65,536 characters**, a limit GitHub does not document but returns in API errors ([Go build commit](https://go.googlesource.com/build/+/823a5f284329c82522056e701c5b21cce25cc411%5E%21/)). There is **no official API for uploading attachments** ([GitHub: attaching files](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)). Anyone with read access can view a comment's edit history, which keeps the original and the most recent 99 edits ([GitHub: tracking changes in a comment](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment)). That is fine for a team chat but worth a line in the opt-in notice. As a side benefit, a colleague away from the board can still read and answer a room from GitHub's own web or mobile UI, since a room is an ordinary issue.

**The third and fourth defaults live in the client.** `gh api` exits with status 1 on a 304 even though the request succeeded ([gh api manual](https://cli.github.com/manual/gh_api)). The board should therefore read `gh auth token` once and call `fetch` with `If-None-Match` itself. It should keep `since` fixed and move it only after a 200, because a new `since` is a new URL and loses the ETag. GraphQL is the wrong tool for the poll: it has no conditional requests and costs at least one point per call ([GitHub GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)), and the board already spends that budget polling PRs. Writes go through one queue, one at a time, spaced a second apart, and back off on 403 or 429.

Three questions remain open, and they decide whether 2–5 s holds in practice: how quickly a new comment shows up in the list endpoint, whether GitHub's `Cache-Control: private, max-age=60` ever returns a stale 304, and whether 304s count toward the secondary budget. None of these is documented. A one-day spike would measure all three.

GitHub's other surfaces each lose to the issue room on at least one axis that matters. **Discussions** add threaded replies, let Read members post and let Triage members moderate ([GitHub: Discussions GraphQL guide](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions)). But they are GraphQL-only, so a 5 s poll costs about 720 points an hour per user that an ETag would have made free. **Gists** need no invitation and only their owner can write them, which suits one "outbox" gist per person. But "secret gists aren't private": anyone with the URL can read them ([GitHub: creating gists](https://docs.github.com/en/get-started/writing-on-github/editing-and-sharing-content-with-gists/creating-gists)), and nobody can remove another person's message. **Git refs** give signed history that works offline. But GitHub recommends **at most 6 pushes per minute per repository** ([GitHub: repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)), rulesets cannot protect custom refs, and confining a collaborator to one branch needs an organization on a paid plan, or GitHub Pro ([GitHub: rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). **Actions** fit only as a moderation bot.

The precedents show the candidate's real advantage. utterances and giscus had to run servers, because an OAuth client secret cannot ship inside a web widget ([giscus](https://github.com/giscus/giscus)). peixAIrada needs no server, because each user's local `gh` already holds a user token. GitHub's Acceptable Use Policies do not forbid passing messages between collaborators. The lines they draw are "automated excessive bulk activity" and "undue burden on our servers through automated means" ([GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)), and a paced chat at human speed stays far from both.

## Peer-to-peer and federated protocols lose on the sleeping Mac

The test that matters most for laptops that sleep is history, and true peer-to-peer fails it: **no pure peer-to-peer stack keeps history unless some peer is always on.**

Trystero is the lightest. It uses public Nostr, MQTT or BitTorrent infrastructure only to introduce peers, then connects them directly over WebRTC, so "your app's data never touches the strategy medium". But it keeps no history, its README suggests an always-on peer "for remembering the last state of data", and it calls the Node path "still experimental" ([Trystero README](https://github.com/dmotz/trystero)). Any WebRTC option also has a TURN problem. Roughly 17.7–20% of WebRTC sessions need a TURN relay ([OpenVidu](https://openvidu.io/blog/2026/06/09/turn-key-considerations/); [100ms](https://www.100ms.live/blog/webrtc-turn-server)). Free tiers such as Metered's 20 GB a month are far more than a text chat uses ([Metered Open Relay](https://www.metered.ca/tools/openrelay/)), but their credentials cannot live in a public repo.

js-libp2p is losing its sponsor. Shipyard ended its contributions on 2026-09-30 and is stepping away from the IPFS bootstrap nodes ([Shipyard](https://ipshipyard.com/blog/2026-the-end-of-ipfs-at-shipyard/)). The largest measurement of its hole punching found **70% ± 7.1% success, conditional on holding a relay reservation** ([arXiv 2510.27500](https://arxiv.org/html/2510.27500v1)). About 36% of peers behind NAT never get one ([ProbeLab](https://probelab.io/blog/can-libp2p-punch-through-nats/)).

Holepunch is the one stack built for this problem. Autobase merges several writers' logs, and a blind peer "replicates encrypted data but never holds the room encryption key" ([Pear docs: blind peering](https://docs.pears.com/how-to/blind-peering/add-blind-peering-to-a-chat-app/)). But that blind peer is exactly the always-on node the brief rules out. Hole punching also "will fail if both the client peer and the server peer are on randomizing NATs", and there is no relaying by default ([Pear docs: HyperDHT](https://docs.pears.com/building-blocks/hyperdht)).

Iroh reached 1.0 on 2026-06-15 ([iroh blog](https://iroh.computer/blog/v1)). But its Node binding exposes only endpoints and QUIC streams, with no gossip or documents ([npm @number0/iroh](https://registry.npmjs.org/@number0/iroh)), and n0's public relays carry "no uptime or performance guarantees" ([iroh docs: relays](https://docs.iroh.computer/concepts/relays)).

Overlay networks make direct HTTP between boards trivial, but break the budget. Tailscale's free plan is non-commercial and capped at six users ([Tailscale pricing FAQ](https://tailscale.com/kb/1251/pricing-faq)), ZeroTier's at ten devices ([ZeroTier pricing](https://www.zerotier.com/pricing.md)), and NetBird's at five users ([NetBird pricing](https://netbird.io/pricing)). Every overlay also needs the board to listen on an interface beyond loopback. mDNS never leaves one subnet ([Cisco](https://www.cisco.com/c/it_it/support/docs/wireless/wireless-lan-controller-software/210835-Troubleshooting-mDNS.html)).

**Verdict against the issue room:** peer-to-peer wins only on latency and loses on history, identity and effort. Its sensible role is a live channel added later on top of the GitHub roster, not a replacement.

Nostr is the strongest federated contender, and the natural home for anonymous users. Identity is just a keypair. `nostr-tools` 2.25.2 is pure ESM, and its only dependencies are the `@noble`, `@scure` and `nostr-wasm` packages ([npm nostr-tools](https://www.npmjs.com/package/nostr-tools)). Free relays such as relay.damus.io and nos.lol answered in the probe, with message caps from 128 KB to 1 MB ([relay.damus.io](https://relay.damus.io); [nos.lol](https://nos.lol)). A Mac that wakes catches up with a `since` filter.

Group chat is the weak spot. **NIP-29 groups need a relay that enforces them**, and in the probe most public NIP-29 relays were dead: one returned HTTP 502 ([relay.groups.nip29.com](https://relay.groups.nip29.com)), others failed DNS or TLS, and only pyramid answered ([pyramid.fiatjaf.com](https://pyramid.fiatjaf.com)). NIP-17 encrypted group DMs are meant for ten people or fewer, and "adding or removing a member starts a new room with empty history" ([NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md)). Marmot brings MLS to Nostr and has Least Authority audits ([Least Authority](https://leastauthority.com/white-noise-marmot-protocol-review-summary-report/)). But its TypeScript port is at 0.5.1 ([npm marmot-ts](https://www.npmjs.com/package/@internet-privacy/marmot-ts)), and its flagship app's repository was archived in a 2026 reorganization ([White Noise](https://github.com/marmot-protocol/whitenoise)). Most important, **none of the free relays probed states a retention policy.** Durable history needs a paid inbox relay at about 2,500 sats a month ([inbox.nostr.wine](https://inbox.nostr.wine)) or a self-hosted strfry.

**Verdict against the issue room:** Nostr loses on authenticated identity and durable history, wins on latency and anonymity, and matches it on zero infrastructure. It is a complement, not a substitute.

Matrix has the richest chat model: history kept by the server, power levels and ACLs. But **matrix.org no longer allows sign-up through the API**. `/register` returns `M_FORBIDDEN`, guest registration included ([matrix.org client API](https://matrix-client.matrix.org/_matrix/client/versions)), and the browser sign-up needs reCAPTCHA v2 and an email ([account.matrix.org](https://account.matrix.org/register)). The device-code grant would let the app get a token once the account exists ([matrix.org auth metadata](https://matrix-client.matrix.org/_matrix/client/v1/auth_metadata)). But in Node, `matrix-js-sdk` keeps E2EE keys only in "an ephemeral in-memory store" ([matrix-js-sdk](https://github.com/matrix-org/matrix-js-sdk)). A self-hosted homeserver (Synapse or Tuwunel) with Matrix Authentication Service could make GitHub the login ([MAS SSO docs](https://github.com/element-hq/matrix-authentication-service/blob/main/docs/setup/sso.md)). That is the best authenticated experience of any option, and also the clearest case of always-on infrastructure.

Delta Chat over chatmail handles anonymity well. It gives instant random addresses with no phone number or email, enforces encryption, ships a prebuilt binary for darwin-arm64 that the Node server talks to over stdio JSON-RPC ([npm @deltachat/stdio-rpc-server](https://www.npmjs.com/package/@deltachat/stdio-rpc-server)), and has 25 interoperable public relays ([chatmail relays](https://chatmail.at/relays)). But relays delete mail after **20 days** by default and cap a mailbox at 500 MB ([chatmail.ini](https://github.com/chatmail/relay/blob/main/chatmaild/src/chatmaild/ini/chatmail.ini.f)). History lives on devices, and forward secrecy waits on Autocrypt v2 ([Delta Chat FAQ](https://delta.chat/en/help)).

The other secure messengers are weaker still. SSB is dormant ([npm ssb-server](https://www.npmjs.com/package/ssb-server)), XMTP charges per message in USDC ([XMTP docs](https://docs.xmtp.org/fund-agents-apps/get-started)), and SimpleX compiles a node-gyp addon and is licensed AGPL-3.0 ([npm simplex-chat](https://www.npmjs.com/package/simplex-chat)).

CRDT engines are a sync layer, not a network, and they bring no identity. The free infrastructure for them is unfit. sync.automerge.org "is not a private instance" and has "no reliability or data safety guarantees" ([Automerge](https://automerge.org/docs/tutorial/network-sync/)). y-webrtc's advertised signaling servers no longer resolve ([y-webrtc](https://github.com/yjs/y-webrtc)). Jazz is a "2.0 alpha with an entirely new API" ([Jazz](https://github.com/garden-co/jazz)), and DXOS is source-available under the Functional Source License ([npm @dxos/client](https://www.npmjs.com/package/@dxos/client)). An append-only log of messages with unique ids needs no merge semantics anyway. CRDTs lose outright.

## Hosted relays and chat platforms trip on the public repo

Every hosted option runs into one structural fact: **peixAIrada is cloned from a public repo, so any key in its code is public.**

Keyless relays get around this by making the topic name the password. ntfy.sh needs no account, but it is a notification service: a **12-hour message cache**, **250 messages a day per visitor** counted by IP, and 4,096-byte messages ([ntfy publish docs](https://raw.githubusercontent.com/binwiederhier/ntfy/main/docs/publish.md)). Its end-to-end encryption request has been open since 2021 ([ntfy issue #69](https://github.com/binwiederhier/ntfy/issues/69)), and its terms promise only "best effort" ([ntfy terms](https://docs.ntfy.sh/terms/)). Behind a corporate NAT, the whole team shares one IP's 250 messages. Public MQTT brokers are test services ("don't publish sensitive information, since anyone could be listening" — [test.mosquitto.org](https://test.mosquitto.org/)), and a retained message keeps only the last message on a topic.

The commercial pub/sub vendors all need a server holding a secret. Ably says "never use API keys in client-side code", and its keys "don't expire" ([Ably auth](https://ably.com/docs/auth)). PubNub keys, without Access Manager, give "unrestricted access to every resource on that keyset" ([PubNub access control](https://www.pubnub.com/docs/general/security/access-control)). Pusher's private channels need a token signed by your server ([Pusher authorization](https://pusher.com/docs/channels/server_api/authorizing-users/)). Their free tiers would fit (Ably: 6M messages a month, one day of history — [Ably pricing](https://ably.com/pricing)). But once a token server exists, the vendor adds little.

The backend-as-a-service and small-host options each have a dealbreaker. Supabase's publishable key is "safe to expose" ([Supabase API keys](https://supabase.com/docs/guides/api/api-keys)) and it supports anonymous sign-ins ([Supabase anonymous sign-ins](https://supabase.com/docs/guides/auth/auth-anonymous)). But free projects **pause after a week of low activity** ([Supabase pricing](https://supabase.com/pricing)), and GitHub sign-in needs an OAuth secret in its dashboard. InstantDB's cloud shuts down on 2027-08-31 ([Instant](https://instantdb.com/essays/instant_team_joins_openai)). Render's free tier sleeps after 15 minutes and takes about a minute to wake ([Render](https://render.com/docs/free)). Fly.io has no free tier for new organizations ([Fly.io pricing](https://docs.fly.io/about/pricing)). Deno Deploy shuts idle apps down after 20–30 s ([Deno Deploy pricing](https://deno.com/deploy/pricing)).

One hosted option does rival the issue room: a Cloudflare Worker with one SQLite-backed Durable Object per room. **Durable Objects run on the Workers Free plan**, which gives 100,000 requests and 13,000 GB-s of duration a day, and incoming WebSocket messages are billed at 20 to 1 ([Cloudflare DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). Sockets parked in hibernation accrue no duration charges ([Cloudflare DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)), and Cloudflare's own hibernating chat-server example is about 120 lines ([Cloudflare hibernation example](https://developers.cloudflare.com/durable-objects/examples/websocket-hibernation-server/)). Thirty people posting 100 messages a day send 3,000 incoming messages, which bill as 150 requests. Even a room that never hibernates uses 10,800 of the 13,000 daily GB-s.

The Worker needs no secret of its own. It can check a GitHub identity through a device-flow OAuth app, for which "the client_secret is not needed" ([GitHub: authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)), requesting no scopes so the token can read only public profile data ([GitHub: OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)). Or it can use an SSH-signature challenge checked against the user's public keys. The same Worker can accept anonymous sockets, keep durable history, and enforce bans and rate limits itself.

The costs are a Cloudflare account for the maintainer, a second codebase, and the fact that "deploying a new version restarts every Durable Object", dropping every socket ([Cloudflare DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). Because the Worker would live in the public repo, any colleague could redeploy it to their own account and change one URL, which limits the risk of depending on one maintainer. **Verdict against the issue room:** the Worker is the only hosted rival. It is ahead on latency, anonymity and server-side moderation, and behind on the one constraint that matters most: no account for the maintainer.

Team chat platforms bring history and moderation with them, but tie the group to a workspace and to per-user secrets.

Slack cut `conversations.history` to **1 request per minute and 15 objects** in 2025, but only for commercially distributed apps outside its Marketplace. Internal apps keep Tier 3 ([Slack changelog](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps)), so each organization would have to create its own app from a manifest shipped in the repo. Socket Mode allows at most 10 connections and delivers each event to any one of them ([Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode)), so 30 copies would have to poll and share roughly 50 calls a minute per workspace. Shared channels across organizations (Slack Connect) need every organization on a paid plan, and the Free plan keeps 90 days of history ([Slack Free plan](https://slack.com/help/articles/7050776459923-Pricing-changes-for-the-Pro-plan-and-updates-to-the-Free-plan)).

Discord forbids automating user accounts ([Discord support](https://support.discord.com/hc/articles/115002192352)). Everyone would post as a shared bot, or through webhooks whose display name the sender sets freely ([Discord webhooks](https://docs.discord.com/developers/resources/webhook)), and text messages "are not end-to-end encrypted" ([Discord](https://discord.com/blog/every-voice-and-video-call-on-discord-is-now-end-to-end-encrypted)).

Telegram bots fetch updates with `getUpdates`, and each fetch marks earlier updates as received for every poller sharing the bot. Updates are kept for at most 24 hours ([Telegram Bot API](https://core.telegram.org/bots/api)). Microsoft Teams change notifications do not support personal Microsoft accounts ([Microsoft Graph](https://learn.microsoft.com/en-us/graph/teams-changenotifications-chatmessage)), and Google Chat apps need a paid Workspace account and a Cloud project with billing ([Google Chat quickstart](https://developers.google.com/workspace/chat/quickstart/gcf-app)).

Zulip Cloud Free fits best. Each person has their own API key (HTTP Basic auth), the board can long-poll an event queue that idles for up to seven days without needing a public URL ([Zulip register queue](https://zulip.com/api/register-queue)), and messages are Markdown. Free is limited to 10,000 messages of search history and 5 GB of storage ([Zulip plans](https://zulip.com/plans/)). **Verdict:** Zulip is a close second for a team willing to create one more account each. The other platforms lose on identity or on delivering to every copy.

There is also a zero-code alternative: opening Slack's or Zulip's own web client in a pane tab. That keeps untrusted text out of the board's process entirely. But Slack blocks browsers it considers unsupported ([Slack support lifecycle](https://slack.com/help/articles/1500001836081-Slack-support-lifecycle-for-operating-systems-app-versions-and-browsers)), and WKWebView reports a frozen WebKit version in its user agent ([WebKit bug 278284](https://auto-bugs.webkit.org/show_bug.cgi?id=278284)). Test it in the app before building anything.

## Anonymous users need keys, not accounts

Inside GitHub, "anonymous" reduces to "has a GitHub account". GitHub removed anonymous gist creation in 2018 ([GitHub blog](https://github.blog/2018-03-20-removing-anonymous-gist-creation)), and every write needs an account with access. Unauthenticated reads of public content get 60 requests per hour per IP, tightened further in 2025 ([GitHub changelog](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/)). A shared machine account is permitted ("multiple users may direct the actions of a machine account"). But its token cannot ship in a public app, and "you may not share API tokens to exceed GitHub's rate limitations" ([GitHub Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). The relay that would hold that token is the always-on infrastructure the brief forbids. Anonymity therefore needs a transport where identity is a keypair: Nostr, a Worker, Trystero or Delta Chat.

In that keyed lane, each install generates an Ed25519 device key. A sender's chosen display name is only a claim. The board shows the reader's own local name for that sender (a "petname") plus a short fingerprint of the key, the standard way to name people without a central registry ([Stiegler, petname systems](http://www.skyhunter.com/marcs/petnames/IntroPetNames.html)). It pins each name to its key on first sight and flags a familiar name arriving under a new key.

An invite is a capability. The room secret travels in the URL fragment, which the client never sends to a server ([RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986#section-3.5)), and HKDF (a key-derivation function) turns it into both the relay topic and the encryption key. The room key also keeps spam out: a message from a non-member fails decryption and is dropped before rendering. On top of that come per-key rate limits, local block lists, and NIP-13 proof of work for genuinely open rooms ([NIP-13](https://github.com/nostr-protocol/nips/blob/master/13.md)).

A colleague in the keyed lane can still carry a verified GitHub mark, through their SSH keys. GitHub publishes each user's SSH signing keys to anyone ([GitHub REST: SSH signing keys](https://docs.github.com/en/rest/users/ssh-signing-keys)), and their authentication keys at `github.com/<user>.keys` ([GitHub REST: user keys](https://docs.github.com/en/rest/users/keys)). The board signs one binding statement (GitHub login, device key, expiry) with `ssh-keygen -Y sign` under a dedicated namespace such as `peixairada-chat-device@v1`; a signature made under one namespace fails verification under any other ([ssh-keygen](https://man.openbsd.org/ssh-keygen)). Peers check that statement once against the user's published keys, then check each message's Ed25519 signature in plain Node.

The SSHSIG format is simple enough (a magic preamble, the namespace, a hash algorithm and a digest — [PROTOCOL.sshsig](https://raw.githubusercontent.com/openssh/openssh-portable/master/PROTOCOL.sshsig)) that the research verified Ed25519 and RSA signatures with `node:crypto` alone ([Node crypto](https://nodejs.org/api/crypto.html)). A hardware security key is touched once, at setup, not once per message. GitHub keeps a commit verified even after its key is removed ([GitHub: commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)), but the chat has no such record and must keep its own. Users without an SSH key can fall back on a NIP-39 gist proof ([NIP-39](https://github.com/nostr-protocol/nips/blob/master/39.md)), which `gh`'s `gist` scope can create. One rule is absolute: **the `gh` token never goes to a relay.** It carries `repo` scope.

The two lanes need different encryption. In the GitHub lane, GitHub itself enforces membership and removal, and its terms say personnel will not access private repository content without consent, except for security, automated scanning and support ([GitHub Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). Plaintext is consistent with that.

In the keyed lane, end-to-end encryption is mandatory, and an **epoch room key** is the right default. Each epoch has 32 random bytes of key. Each message is sealed with XChaCha20-Poly1305, whose 24-byte nonces sidestep AES-GCM's limit of 2^32 messages per key with random IVs ([NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)), and carries the sender's Ed25519 signature inside the ciphertext. Associated data binds room, epoch, sender and message id. On a removal, an admin seals a new key to each remaining member, which is N−1 small boxes. It is about 200 lines on Node's core crypto. Like NIP-44, it offers no forward secrecy and no post-compromise security ([NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md)).

The heavier schemes buy little here. Sender Keys meets only "a weak notion of security" ([ePrint 2023/1385](https://eprint.iacr.org/2023/1385)). Megolm has no post-compromise security within a session ([ePrint 2023/485](https://eprint.iacr.org/2023/485.pdf)). MLS is the real thing, but RFC 9750 warns that the server relaying messages can "reorder messages or provide an inconsistent view to different users", and that MLS itself enforces no access control on group changes ([RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.html)). Its only pure-JS implementation "has not undergone a formal security audit" ([ts-mls](https://github.com/LukaJCB/ts-mls)). libsignal states that "use outside of Signal is unsupported" ([libsignal](https://github.com/signalapp/libsignal)). The deciding argument is local. Anyone who takes over a colleague's Mac already controls terminals running Claude Code, and the chat shows history in plaintext anyway. The realistic threats are the relay operator and a removed colleague, and an epoch key handles both.

Moderation without a server works in three layers. The first is local blocks, which always work. The second is signed roster and moderator events that honest clients obey. Each roster version is hash-chained to the last, so neither a relay nor a member can add someone silently; that was the root of the practical attacks on Matrix, where the server controlled group membership ([ePrint 2023/485](https://eprint.iacr.org/2023/485.pdf)). The third is key rotation, the only step that actually cuts someone off.

Edits and deletes are signed requests, honored only from the original device key or a roster admin. A delete cannot recall copies others already hold: even Nostr's deletion is only a request ([NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md)). A Worker could additionally drop writes from banned keys. In the GitHub lane, moderation is GitHub's own: Write members hide and delete comments, and Admins remove collaborators.

## Chat text must never reach a drawer

The dangerous component is the board, not the transport. The board renders markdown, opens URLs in a pane, turns file paths into editor links, and can type into terminals running Claude Code: through `sendToClaude`, `typeInShell`, `answerInDrawer` and a notification's *Reply…*. A colleague's message, or a stranger's in a guest room, is hostile HTML and, worse, hostile instructions. OWASP ranks prompt injection first, notes that no method fully prevents it, and recommends least privilege, a human in the loop, and to "separate and clearly denote untrusted content" ([OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). Anthropic's own guidance warns that agents "can take unintended actions due to prompt injection" ([Claude Agent SDK: secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment)).

**Isolation should be structural, not a convention.** Chat lives in its own module whose only outputs are DOM nodes, and a test asserts that no chat code path reaches the drawer APIs or a holder socket. Any later "ask Claude about this message" must be an explicit click that shows the text and passes it on as quoted, untrusted data. Chat text is stripped of control characters and ANSI escapes before display. Alerts say "New message in #room from <name>" instead of echoing text that could imitate a system prompt.

Rendering needs a stricter sanitizer than the transcript's. "Marked does not sanitize the output HTML" ([marked](https://github.com/markedjs/marked)), so the board's DOMPurify setup is the starting point, tightened for other people's words. That means HTML only, with no SVG or MathML, and no `data-` attributes. It means **no images at all**, since even `data:` images can impersonate the board's interface. It means no `id` or `name` attributes, which could clobber the board's own `#log`, `#term` and `#hmenu`. Links are allowed only for `https:` and `mailto:`, and raw HTML is stripped in marked rather than left to the sanitizer. DOMPurify itself warns that unknown protocols are an XSS risk, and that changing markup after sanitizing can "void the effects of sanitization" ([DOMPurify](https://github.com/cure53/DOMPurify)).

The board's path linkifier must never run on chat: no `vscode:`, `zed:`, `file:`, `javascript:` or `peixairada:` links, and a click shows the full URL before anything opens. The vendored DOMPurify 3.4.14 and marked 18.0.11 should move to 3.4.17 ([npm dompurify](https://www.npmjs.com/package/dompurify)) and 18.1.1 ([npm marked](https://www.npmjs.com/package/marked)).

The network side stays narrow. Chat makes outbound connections only, and nothing listens beyond 127.0.0.1. WebRTC encrypts with DTLS ([RFC 8827](https://www.rfc-editor.org/rfc/rfc8827)) but reveals IP addresses to peers through its connection candidates, so any WebRTC path should be opt-in.

Each message in the keyed lane is checked in a fixed order: a size cap before decoding, then decryption with the room and epoch bound in, then the sender's signature, then the roster. Messages are de-duplicated by the hash of the envelope, timestamps more than about five minutes in the future are rejected, and each sender's sequence numbers are tracked.

Keys go in the Keychain, written with `security -i` from stdin as the board already stores the Jira token, never with the secret on the command line, and never under `~/.claude`. New chat routes need the board's key, like every other route. Third-party relays see metadata even when content is encrypted: ntfy logs topic names and IP addresses ([ntfy FAQ](https://docs.ntfy.sh/faq/)), and NIP-44 lists IP and date leaks ([NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md)). So the first-use notice should name the relays in use.

## Recommendation: ship the issue room, add a keyed guest lane later

**Version 1 is the issue room, behind a Settings switch that is off by default.** One private, chat-only repo is owned by a free organization, with members as Read and moderators as Write, and each room is an issue. The board runs one repo-wide REST poll with an ETag through `fetch`, every 2–5 s while it is in view and slower while it is hidden. It sets `subscription {ignored: true}` the moment chat is enabled, and sends and accepts invitations through the collaborators and invitations endpoints, re-sending them after seven days. It sends one write at a time, spaced a second apart, caps messages client-side at about 60,000 characters, and renders through the tightened sanitizer with no route from chat to a drawer. GitHub supplies identity, history, membership, moderation and a mobile client for free, and the board's existing `gh` plumbing does most of the work. The chat repo can also hold a roster file mapping GitHub logins to device keys, so the second lane inherits an authenticated membership list.

**Version 2, only if anonymous users are truly wanted, is a keyed guest lane on Nostr.** Rooms are capability links with the secret in the fragment. Each message is signed by a device key, encrypted under the epoch key, and sent to two or three free relays at once for redundancy. A woken board catches up with `since` and keeps a local archive. Names show as petname plus fingerprint, with a verified mark from the SSH binding. The lane adds no account, server or dependency beyond `nostr-tools`.

If the group later wants faster delivery, durable guest history and bans enforced on the server, the Cloudflare Durable Object is the upgrade. It is free, small enough to read in one sitting, and redeployable by anyone from the public repo. Both lanes should sit behind one envelope and one renderer, with a `relay` setting, so the choice can be reversed.

The rest should be skipped. Discussions, gists and git refs are each beaten on cost, privacy or throughput. libp2p's public infrastructure is losing its operator, and the overlay networks' free tiers exclude this use. Matrix needs manual sign-up or a server, and Supabase pauses. The pub/sub vendors need a token server, and Slack, Discord and Telegram stumble on tokens and on delivering to every copy. CRDT engines need a sync server and bring no identity.

**Two checks come before any build.** The first is the one-day spike on how quickly a comment becomes visible, on stale 304s, and on whether 304s count toward the secondary budget. The second is a ten-minute test of whether Slack's or Zulip's web client loads in the WKWebView pane: if the group already shares one, that may be the cheapest chat of all.

## Conclusion

The decisive asset is not GitHub's storage but the `gh` token already signed in on every Mac. That token removes the problem that forced utterances and giscus to run servers, and the one that sinks every vendor whose key would have to sit in a public repo. Whichever transport carries the bytes, GitHub stays the root of identity: the repo's collaborator list for colleagues, and the published SSH keys for anyone in a keyed room. The lanes also invert each other's trust model. In the issue room the server is the access control, so plaintext is acceptable and moderation comes free. On public relays the key is the access control, the relay is a dumb pipe, and encryption is not optional. Treating anonymity as a second lane that shares the envelope and renderer, rather than as a feature to force onto one transport, keeps both honest.

The security budget belongs at the board's input boundary, not in the cryptography. Post-compromise security and MLS protect against an attacker who already holds a device, and on this app that attacker already controls terminals running Claude Code. What actually prevents harm is a chat module that can only produce DOM nodes, a sanitizer stricter than the transcript's, and a test proving no chat path reaches a drawer. Those carry over unchanged to whichever transport wins next.
